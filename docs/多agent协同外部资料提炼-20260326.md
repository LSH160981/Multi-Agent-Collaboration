## 核心收获

### 1. 平台与 skill 的边界要清楚

OpenClaw 平台已经有：
- session 生命周期
- tool 调用
- system prompt 注入
- command / skill 入口
- TUI / CLI / Gateway

所以本 skill 应该：
- 定义公司化协作方法论
- 约束角色边界
- 把用户入口 `/mac`、默认接管、消息治理、审核、恢复写清
- 借助 session 能力组织团队

而不是：
- 在文档里再造一层平台
- 把 CLI 脚本误当作平台能力本身

### 2. 多 Agent 的最小闭环不是“大团队”，而是“可验证闭环”

参考优秀作品后，最小闭环其实是：
- 主Agent / Orchestrator
- Worker / Builder
- Reviewer
- 明确 handoff
- 明确状态机
- 明确失败终点

这比一上来预建十几个角色更真实，也更稳。

### 3. 你手稿里的“双组竞争 + 审核 + 检查 + 动态招聘”方向没错，但要分层实现

建议分三层：

#### A. 平台原生层
- `sessions_spawn`
- `sessions_send`
- `sessions_history`
- `sessions_list`
- `sessions_yield`
- `tools.agentToAgent.enabled`
- `tools.agentToAgent.allow`

#### B. skill 纪律层
- 主Agent唯一用户出口
- 非主Agent禁止联系用户
- `/mac` 强触发
- 复杂任务默认接管
- 最小团队优先
- A/B 双组只在有价值时启用

#### C. 仓库脚本/烟测层
- 安装脚本
- 自检脚本
- 握手测试
- 静默任务测试
- 恢复测试
- runtime smoke demo

### 4. 伪代码和逻辑流程必须继续保留，而且要用中文

因为你要的不只是一个可运行仓库，而是：
- 项目骨架
- 中文伪代码
- 中文逻辑执行流程
- 别人是怎么推导出系统结构的

这个方向是对的，应该继续保留在 skill 与 docs 中。

### 5. 自学习不能直接改主 skill，必须先 research 再审核吸收

外部资料很多，但不能让脚本自动野蛮改仓库。
正确闭环：
1. 抓取资料
2. 写入 `research/`
3. 审核Agent给出吸收建议
4. 主Agent决定改 skill / docs / scripts 哪部分
5. git 记录

## 对当前仓库的具体改进建议

1. 在安装文档中明确真实配置字段：`tools.agentToAgent.enabled`、`tools.agentToAgent.allow`
2. 在 `/mac` 文档中明确：slash command 入口和纯文本触发词都支持
3. 在项目骨架文档中明确：skill 层 vs CLI 适配层
4. 在测试文档中增加：先通信、再静默任务、再恢复链路
5. 在 research 下持续保存网页提取文本与仓库观察笔记

## 一句话总结

**最好的方向不是“角色越多越强”，而是“OpenClaw 原生 session + 严格纪律 + 结构化 handoff + 审核恢复闭环”。**
