# OpenClaw 原生多会话改造方案（2026-03-27）

> 目标：把 `Multi-Agent-Collaboration` 从“会生成任务包、会跑 demo、会做 smoke test 的 skill 工程仓库”，继续推进为 **真正以 OpenClaw session 为 Agent 运行单元** 的原生多会话协作系统。

---

## 一、先把边界讲清楚

### 1. 平台原生层负责什么
OpenClaw 平台已经原生提供：

- `sessions_spawn`
- `sessions_send`
- `sessions_list`
- `sessions_history`
- `sessions_yield`
- skill 触发与 slash-like skill entry
- agent / session 生命周期
- tool 调用、消息、浏览器、cron、gateway、memory 等能力

### 2. 本 skill 应该负责什么
本 skill 不该重造平台，而应负责：

- 复杂任务什么时候切入多会话
- 主 Agent / AgentPool / Reviewer / Inspect / Specialist 的职责边界
- JSON 任务包与 handoff 契约
- 审核、去重、恢复、降级、扩编策略
- 默认接管、`/mac` 强触发、安装、自检、演示、测试

### 3. 当前仓库的准确定位
当前仓库已经具备：

- `/mac` 命令桥
- 主 skill 方法论
- runtime orchestrator demo
- inspect / recover demo
- 握手 / 静默任务 / smoke / 恢复测试
- 研究资料归档与提炼

但仍有一部分实现是 **CLI 适配层演示**，不是最终的平台原生实现本身。

---

## 二、最终目标形态

```text
用户任务
  -> 主Agent（唯一用户出口）
    -> 判断是否需要多会话
      -> AgentPool 决定复用 / 招聘 / A/B 分组
        -> 用 sessions_spawn 创建所需内部会话
        -> 用 sessions_send 持续派单 / 纠偏 / 催办
        -> 用 sessions_list / sessions_history 做观测与恢复判断
        -> 用 sessions_yield 让前台等待推送式收尾
    -> Reviewer / Inspect / Specialists 回传结构化结果
  -> 主Agent 去重、审查、收口
  -> 用户只收到一条最终有效结论
```

## 三、分阶段落地

## Phase 1：方法论与文档层（已基本完成）

已具备：
- 主 skill + `/mac` skill
- 中文伪代码与中文逻辑流程
- 安装、自检、命令参考、测试说明
- 外部优秀作品提炼

本阶段目标：**让安装、理解、验收、研究沉淀都清晰。**

## Phase 2：CLI 适配 demo 层（已完成基础骨架）

已具备：
- `runtime_sessions.py`
- `runtime_orchestrator.py`
- `inspect_and_recover.py`
- 各类 smoke tests

本阶段价值：**先把协作闭环跑通，并且让结果可落盘、可回归、可观察。**

## Phase 3：真正接到 OpenClaw session tools（下一阶段重点）

应该逐步把下面几件事接实：

### 1. 派单真正使用 `sessions_spawn`
适用场景：
- 新角色缺口
- 用户明确要独立持续线程
- 需要 reviewer / verifier / researcher / debugger 等内部分工

### 2. 追派/纠偏真正使用 `sessions_send`
适用场景：
- 返工
- 增补约束
- reviewer 驳回后重新下发
- stale 以后强制唤醒

### 3. 巡检真正使用 `sessions_list` + `sessions_history`
适用场景：
- 会话是否存在
- 最近是否活跃
- 是否只是慢，还是已经跑偏/卡死
- 是否已有成果可复用

### 4. 主会话用 `sessions_yield` 交还前台
适用场景：
- 派单已完成
- 当前无需前台占着等
- 想改为推送式完成通知

## 四、推荐的原生调度动作语义

建议统一成下面这些动作：

### 1. `reuse`
复用现有 session，而不是无脑新建。

### 2. `spawn`
缺角色才创建新会话。

### 3. `dispatch`
发首次任务包。

### 4. `steer`
发现方向偏了，补发纠偏消息。

### 5. `probe`
检查最近活跃度、产出、阻塞点。

### 6. `resume`
继续已有会话，不重复灌背景。

### 7. `redispatch`
原会话不适合继续，重派给别的会话。

### 8. `rebuild`
角色失效、上下文污染或长期 stale，重建整条链路。

## 六、从优秀作品吸收到的关键原则

### 1. opencrew：A2A 要有真实触发链
- 不是发一条消息就算协作了
- 真正触发要靠 `sessions_send`
- sessionKey 不要手写，优先从可见列表复制/解析
- 一个任务尽量绑定一个稳定 thread/session

### 2. OpenMOSS：状态机、审查、日志、巡检要分层
- task / subtask / review / patrol / log 不要混成一锅
- 让 planner / executor / reviewer / patrol 边界清楚
- 恢复与返工要有单独记录面

### 3. ClawHub Agent Team Orchestration：先最小闭环再扩编
- 先 orchestrator + builder + reviewer
- 明确 handoff 五件套：做了什么、产物在哪、怎么验、已知问题、下一步
- orchestrator 不下场抢 worker 的活

### 4. zelikk 两篇 TUI 实战：先测通信再做复杂任务
- 先做 agent 间握手与互发测试
- session 和 agent 要分清
- 少乱用 `/new`
- `sessions_send(timeout=0)` 场景很关键

## 七、关于“平台级默认接管”的真实说法

这个需求可以分成三层，不要混说：

### 1. 方法论默认接管
安装后，复杂任务默认优先按本 skill 的协作纪律来处理。

### 2. 技能入口默认可见
安装到共享 `~/.openclaw/skills` 后：
- 所有 agent 都能读到 `multi-agent-collaboration`
- `/mac` 作为 user-invocable skill，应该在支持原生命令的平台成为 slash-like 入口候选
- 在不显示原生 skill 命令的平台，纯文本 `/mac ...` 仍可作为强触发词

### 3. 平台配置放开 A2A
至少应满足：
- `tools.agentToAgent.enabled = true`
- `tools.agentToAgent.allow` 包含需要互通的 agent id
- 建议：`tools.sessions.visibility = "all"`（或对应等价配置）
- 建议启用 skills 原生命令展示：`commands.nativeSkills = "auto"`

> 注意：本仓库可以提供配置样例与安装说明，但是否“平台级默认接管所有 agent”，最终仍取决于 OpenClaw 配置与用户安装位置。

## 八、自学习能力应该怎么做才不失控

允许“自动学习”，但必须分层：

1. 搜外部资料
2. 落 `research/`
3. 审核 Agent 产出吸收建议
4. 主 Agent 决定是否改 `skills/` / `docs/` / `scripts/`
5. git 记录

绝不能：
- 直接让脚本无审计改主 skill
- 不经 review 自动重写核心协议
- 把外部 prompt 原样混入主规则

> 这个 skill 已经完全变成平台原生多会话系统。

而是：

> 这个 skill 已经具备完整的方法论、协议、安装、自检、测试、研究沉淀和半闭环 runtime demo；下一阶段重点是把派单、巡检、恢复进一步从 CLI 适配层推进到 OpenClaw 原生 session tools 编排层。
