# 平台级接管设计

目标：用户安装本 skill 后，默认就像是在和 Multi-Agent-Collaboration 的主Agent方法论对话。

## 接管思路

### 1. 方法论接管

最现实、最稳的第一步不是强改 OpenClaw 内核，而是：

- 让 skill 文档明确要求复杂任务默认进入多 Agent 流程
- 让 `/mac` 成为显式入口
- 让主Agent方法论成为默认复杂任务处理策略

### 2. 共享技能安装

将 skill 安装到：

- `~/.openclaw/skills/multi-agent-collaboration`

这样所有 Agent 都可见。

### 3. 主Agent 中心化

用户真正看到的只有主Agent。
其他 Agent 只做内部协作。

### 4. 多平台兼容

对 TUI / GUI / TG 的一致性，不强依赖平台原生 slash command 是否存在。
而是：

- 真有 slash command 时，用 `/mac`
- 没有时，把用户发出的 `/mac xxx` 纯文本也视为触发词

## 当前推荐的平台级接管落地方式

### 1. 默认复杂任务接管
- 用户直接发复杂任务：主Agent 先接住，再判断是否进入多会话
- 用户发 `/mac ...`：强制进入多会话协作模式
- 用户点名 `Multi-Agent-Collaboration skill`：等价于显式启用本方法论

### 2. 真正的配置前提
- `tools.agentToAgent.enabled = true`
- `tools.agentToAgent.allow = [当前允许互相通信的 agent id 列表]`
- 推荐让主 skill 与 `/mac` 命令桥安装到共享 skills 目录

### 3. 平台能力与仓库脚本要分层
- 平台原生层：session、skills、commands、agent-to-agent
- 仓库脚本层：安装、自检、烟测、演示、恢复样例

也就是说：
- `/mac` 的真正入口由 skill 暴露
- 原生协作由 session / agent-to-agent 能力承载
- 本仓库脚本只负责辅助安装与测试，不替代平台能力本身
