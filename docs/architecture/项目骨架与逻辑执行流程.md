# 项目骨架与逻辑执行流程

这份文件作为 `Multi-Agent-Collaboration` 的**主架构总纲**，统一回答四件事：

1. 这个 skill 的项目骨架是什么
2. 多 agent / 多 session 怎么推导、怎么通信、怎么恢复
3. 默认接管与 `/mac` 入口如何落地
4. 当前哪些已经代码化，哪些仍是下一阶段工作

## 一、系统骨架

### 1. 用户入口层
用户可以通过三种方式进入：
- 直接发复杂任务
- 发 `/mac XXX`
- 明确点名 `Multi-Agent-Collaboration`

入口统一先交给**主 Agent**。

### 2. 主 Agent（CEO）
职责：
- 理解任务
- 判断信息是否缺失
- 判断是否需要多会话
- 确定交付物
- 下发给 AgentPool / specialist / reviewer / inspect
- 合并去重
- 只输出一条最终结论给用户

### 3. AgentPool（HR / 组织设计）
职责：
- 看能力缺口
- 复用已有 agent / session
- 缺什么再招聘什么
- 维持最小团队原则
- 需要时生成稳健组 / 激进组两套竞争编制

### 4. 专家执行层（specialist / group lead）
职责：
- 只做自己那部分任务
- 按 JSON 任务包执行
- 产出 artifacts / logs / queue 更新
- 不直接联系用户

### 5. 审核 Agent（Reviewer / Judge / Metrics）
职责：
- 审核结构、质量、证据、完整性
- 评分
- 驳回 / 通过
- 给主 Agent 返回可比较的结论

### 6. 检查 Agent（Inspect / Patrol）
职责：
- 看 session 是否活着
- 看队列有没有推进
- 看日志是否有产出
- stale 时发唤醒 / 返工 / 重派 / 重建建议

## 三、默认接管怎么落地

目标不是强改 OpenClaw 内核，而是在现有平台能力上完成**方法论接管**。

### 1. 方法论接管
- 在 `SKILL.md` 中明确：复杂任务默认走多会话流程
- 把 `/mac` 作为显式入口
- 把“主 Agent 唯一用户出口”写成硬规则

### 2. 共享安装接管
- 主 skill 安装到共享 skills 目录
- `/mac` 命令桥也安装到共享 skills 目录
- 让所有相关 agent 都能读到相同方法论

### 3. 初始化接管
- 安装后初始化 `mac-system/`
- 生成核心角色骨架
- 明确提示跑自检、握手测试、静默任务测试、恢复测试

### 4. 对话策略接管
复杂任务进入后，主 Agent 先判断：
- 是否需要拆解
- 是否需要 specialist
- 是否需要 A/B 双组
- 是否需要 reviewer / inspect

而不是默认单 agent 一把梭。

## 四、执行逻辑流程

### 标准流程

1. 用户发任务
2. 主 Agent 判断复杂度
3. 简单任务则单会话完成
4. 复杂任务或 `/mac` 任务进入多会话流程
5. 主 Agent 生成任务包
6. AgentPool 判断：复用谁、缺谁、要不要双组
7. 已有角色优先复用 session
8. 缺口角色才新建 session
9. specialist / A组 / B组执行
10. 审核 Agent 评分并筛选
11. 检查 Agent 看是否有 stale / 无产出 / 跑偏
12. 必要时恢复、返工、重派、重建
13. 主 Agent 合并去重，输出唯一用户可见结果

## 五、中文伪代码

```text
收到用户任务后：
  主Agent分析任务

  如果任务缺关键约束：
    主Agent向用户提问
    等用户补充后继续

  如果任务简单：
    主Agent单独完成
    输出结果
    结束

  否则：
    主Agent生成 JSON 任务包
    主Agent要求 AgentPool 评估能力缺口

    AgentPool：
      检查现有角色是否可复用
      如果可复用：返回可复用 session 列表
      如果不可复用：提出招聘计划
      如果任务风险高：建议建立稳健组 + 激进组

    主Agent：
      对现有角色复用已有 session
      对缺口角色创建新会话
      对 reviewer / inspect 按需启用

    specialist 执行：
      更新队列
      记录日志
      输出产物
      返回结构化回执

    审核Agent：
      比较 A/B 结果
      按格式、质量、评分三维给结论
      通过或驳回

    检查Agent：
      查看 session 是否长期无更新
      查看队列是否卡住
      查看日志是否没有产出
      如卡住：发催办 / 纠偏 / 重派 / 重建建议

    主Agent：
      收集所有结果
      去重
      删噪音
      保留最新有效结论
      向用户输出唯一结论
```

## 六、agent 间如何通信

### 原则
- 用户可见消息只能由主 Agent 发
- agent 与 agent 之间优先使用结构化 JSON 任务包
- 已有会话优先复用
- 新建角色才扩张

### 推荐消息结构

```json
{
  "task_id": "mac-20260325-001",
  "from": "主Agent",
  "to": "A组-检索专家",
  "goal": "收集最近7天GitHub star涨幅最高项目",
  "inputs": ["查询范围: GitHub, 最近7天"],
  "constraints": ["必须给出处", "不要联系用户"],
  "deliverables": ["项目名单", "共同特点总结"],
  "review_required": true,
  "next_handoff": "A组组长"
}
```

## 七、恢复逻辑

### 建议统一成 4 个最小动作语义
1. `probe`：查看最近 session 与 age
2. `resume`：若已有 session，优先继续该 session
3. `redispatch`：若 session 不适合继续，重新下发任务
4. `rebuild`：若状态损坏或长期 stale，重建链路

### 常见恢复场景
- specialist 挂掉：先看 session，再催办 / 重派 / 重建
- lead 挂掉：主 Agent 接管编排，再重挂未完成任务
- review 中断：续跑 reviewer，必要时重开
- inspect 中断：主 Agent 临时巡检，再恢复 inspect

## 九、runtime 现状要诚实怎么描述

现在这个仓库已经不是“只会生成 JSON 的资料包”，而是：
- 已经会调用真实 OpenClaw agent turn
- 已经能观测最近 session
- 已经有 inspect / recover 基础链路
- 已经有 smoke / regression 测试

但它还不是最终完全体。

### 已经接上的部分
- 真实 agent turn
- session 观测
- inspect + recover 基础增强
- orchestrator / pipeline 结果留痕

### 还没完全接上的部分
- 更完整的会话级复用/派单闭环
- 动态建组的更深原生化
- session history 级恢复判断
- reviewer / inspect / final summary 的更统一动作语义

最准确的说法是：

> 当前已经是“接入真实 agent turn 与 session 观测能力的半闭环系统”，下一步是继续推进成更完整的原生多会话闭环。

## 十、平台原生层 vs 仓库脚本层

### 平台原生层
- session 生命周期
- tool 调用
- skills / 显式技能入口
- agent-to-agent 能力
- 历史、压缩、模型、权限等平台能力

### 仓库脚本层
- 安装脚本
- 自检脚本
- smoke test
- runtime demo
- staged pipeline
- 研究资料抓取与整理

结论：
- skill 负责规则、流程、边界、中文伪代码、纪律
- OpenClaw 平台负责真正的 session 与 tool 运行
- 仓库脚本只做安装、自检、演示、落盘与回归
- 仓库不替代平台，只增强协作方法论

## 十一、结论

这套系统真正重要的不是“agent 数量多”，而是：

1. **主 Agent 唯一出口**
2. **已有会话优先复用**
3. **缺口角色才动态扩张**
4. **审核、巡检、恢复闭环真实存在**
5. **状态、日志、队列、评分卡都能留痕**
6. **最终结果只有一个，而且去重过**
