## 一、系统骨架

### 1. 用户入口层
用户通过以下方式进入：
- 直接发复杂任务
- 发 `/mac XXX`
- 明确点名 `Multi-Agent-Collaboration`

入口统一先交给 **主 Agent**。

### 2. 主 Agent（唯一用户出口）
职责：
- 理解任务
- 判断是否需要多会话
- 确定交付物
- 下发给 AgentPool / specialist / reviewer / inspect
- 合并去重
- 对用户只输出一条最终结论

### 3. AgentPool（HR / 组织设计）
职责：
- 看能力缺口
- 复用已有 agent / session
- 缺什么再招聘什么
- 维持最小团队原则
- 需要时生成稳健组 / 激进组两套竞争编制

### 4. 专家执行层（specialist / group lead）
职责：
- 只做自己那部分任务
- 按 JSON 任务包执行
- 产出 artifacts / logs / queue 更新
- 不直接联系用户

### 5. 审核 Agent（Reviewer / Judge / Metrics）
职责：
- 审核结构、质量、证据、完整性
- 评分
- 驳回 / 通过
- 给主 Agent 返回可比较结论

### 6. 检查 Agent（Inspect / Patrol）
职责：
- 看 session 是否活着
- 看队列有没有推进
- 看日志是否有产出
- stale 时发 probe / resume / redispatch / rebuild 建议

## 三、当前推荐主链路

### 正式入口
- 用户入口：`skills/multi-agent-collaboration/SKILL.md`
- `/mac` 入口：`skills/mac/SKILL.md`
- staged pipeline：`scripts/run_staged_pipeline.py`
- runtime orchestrator：`scripts/runtime_orchestrator.py`
- 恢复 / 巡检：`scripts/inspect_and_recover.py`

### 辅助 / demo
- `scripts/runtime_sessions.py`：原生 session 风格 demo / 验收脚本，不作为长期生产调度主入口
- `scripts/runtime_dispatch.py`：底层派发辅助，不是用户主入口
- `scripts/stage1_plan.py` / `stage2_workers.py` / `stage3_review_final.py`：staged pipeline 子阶段脚本

## 四、默认执行逻辑

1. 用户发任务
2. 主 Agent 判断复杂度
3. 简单任务单会话完成
4. 复杂任务或 `/mac` 任务进入多会话流程
5. 主 Agent 生成任务包
6. AgentPool 判断：复用谁、缺谁、要不要双组
7. 优先复用已有 session
8. specialist / A组 / B组执行
9. 审核 Agent 评分并筛选
10. 检查 Agent 看是否 stale / 无产出 / 跑偏
11. 必要时恢复、返工、重派、重建
12. 主 Agent 合并去重，输出唯一用户可见结果

## 九、runtime 现状要诚实怎么描述

现在这个仓库已经不是“只会生成 JSON 的资料包”，而是：
- 已经会调用真实 OpenClaw agent turn
- 已经能观测最近 session
- 已经有 inspect / recover 基础链路
- 已经有 smoke / regression 测试

但它还不是最终完全体。

### 已经接上的部分
- 真实 agent turn
- session 观测
- inspect + recover 基础增强
- orchestrator / pipeline 结果留痕

### 还没完全接上的部分
- 更完整的会话级复用/派单闭环
- 动态建组的更深原生化
- session history 级恢复判断
- reviewer / inspect / final summary 的更统一动作语义

最准确的说法是：

> 当前已经是“接入真实 agent turn 与 session 观测能力的半闭环系统”，下一步是继续推进成更完整的原生多会话闭环。

## 十、平台原生层 vs 仓库脚本层

### 平台原生层
- session 生命周期
- tool 调用
- skills / 显式技能入口
- agent-to-agent 能力
- 历史、压缩、模型、权限等平台能力

### 仓库脚本层
- 安装脚本
- 自检脚本
- smoke test
- runtime demo
- staged pipeline
- 研究资料抓取与整理

结论：
- skill 负责规则、流程、边界、中文伪代码、纪律
- OpenClaw 平台负责真正的 session 与 tool 运行
- 仓库脚本只做安装、自检、演示、落盘与回归
- 仓库不替代平台，只增强协作方法论

## 十一、结论

这套系统真正重要的不是“agent 数量多”，而是：

1. **主 Agent 唯一出口**
2. **已有会话优先复用**
3. **缺口角色才动态扩张**
4. **审核、巡检、恢复闭环真实存在**
5. **状态、日志、队列、评分卡都能留痕**
6. **最终结果只有一个，而且去重过**
