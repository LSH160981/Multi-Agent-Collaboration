这份文件专门回答三个问题：

1. **这个 skill 的项目骨架是什么？**

## 一、项目骨架（中文）

### 1. 用户入口层
- 用户直接发复杂任务
- 用户发 `/mac XXX`
- 用户点名 `Multi-Agent-Collaboration skill`

入口统一交给 **主Agent**。

### 2. 主Agent（CEO）
职责：
- 理解任务
- 判断信息是否缺失
- 判断是否需要多会话
- 确定交付物
- 下发给 AgentPool / specialist / reviewer / inspect
- 合并去重
- 只输出一条最终结论给用户

### 3. AgentPool（HR / 组织设计）
职责：
- 看能力缺口
- 复用已有 agent / session
- 缺什么再招聘什么
- 维持最小团队原则
- 需要时生成稳健组 / 激进组两套竞争编制

### 4. 专家执行层（specialist / group lead）
职责：
- 只做自己那部分任务
- 按 JSON 任务包执行
- 产出 artifacts / logs / queue 更新
- 不直接联系用户

### 5. 审核Agent（Reviewer / Judge / Metrics）
职责：
- 审核结构、质量、证据、完整性
- 评分
- 驳回 / 通过
- 给主Agent返回可比较的结论

### 6. 检查Agent（Inspect / Patrol）
职责：
- 看 session 是否活着
- 看队列有没有推进
- 看日志是否有产出
- stale 时发唤醒 / 返工 / 重派 / 重建建议

## 三、执行逻辑流程（中文）

### 标准流程

1. 用户发任务
2. 主Agent 判断复杂度
3. 简单任务则单会话完成
4. 复杂任务或 `/mac` 任务进入多会话流程
5. 主Agent 生成任务包
6. AgentPool 判断：复用谁、缺谁、要不要双组
7. 已有角色优先 `sessions_send`
8. 缺口角色才 `sessions_spawn`
9. specialist / A组 / B组执行
10. 审核Agent 评分并筛选
11. 检查Agent 看是否有 stale / 无产出 / 跑偏
12. 必要时恢复、返工、重派、重建
13. 主Agent 合并去重，输出唯一用户可见结果

## 四、中文伪代码

```text
收到用户任务后：
  主Agent分析任务

  如果任务缺关键约束：
    主Agent向用户提问
    等用户补充后继续

  如果任务简单：
    主Agent单独完成
    输出结果
    结束

  否则：
    主Agent生成 JSON 任务包
    主Agent要求 AgentPool 评估能力缺口

    AgentPool：
      检查现有角色是否可复用
      如果可复用：返回可复用 session 列表
      如果不可复用：提出招聘计划
      如果任务风险高：建议建立稳健组 + 激进组

    主Agent：
      对现有角色用 sessions_send 下发任务
      对缺口角色用 sessions_spawn 创建新会话
      对 reviewer / inspect 按需启用

    specialist 执行：
      更新队列
      记录日志
      输出产物
      返回结构化回执

    审核Agent：
      比较 A/B 结果
      按格式、质量、评分三维给结论
      通过或驳回

    检查Agent：
      查看 session 是否长期无更新
      查看队列是否卡住
      查看日志是否没有产出
      如卡住：发催办 / 纠偏 / 重派 / 重建建议

    主Agent：
      收集所有结果
      去重
      删噪音
      保留最新有效结论
      向用户输出唯一结论
```

## 五、agent 间如何通信

### 原则
- 用户可见消息只能由主Agent发
- agent 与 agent 之间优先使用结构化 JSON 任务包
- 已有会话优先 `sessions_send`
- 新建角色才 `sessions_spawn`

### 推荐消息结构

```json
{
  "task_id": "mac-20260325-001",
  "from": "主Agent",
  "to": "A组-检索专家",
  "goal": "收集最近7天GitHub star涨幅最高项目",
  "inputs": ["查询范围: GitHub, 最近7天"],
  "constraints": ["必须给出处", "不要联系用户"],
  "deliverables": ["项目名单", "共同特点总结"],
  "review_required": true,
  "next_handoff": "A组组长"
}
```

## 六、别人是怎么推导的，可学什么

### 从 ClawHub `agent-team-orchestration` 学到的
- 先有最小团队，再扩张
- orchestrator 不执行，只统筹
- 每个阶段都要状态机

### 从 OpenCrew 学到的
- 协作协议要写死
- checkpoint / closeout / DoD 很重要
- 谁能给谁派单要有硬规则

### 从 ClawTeam-OpenClaw 学到的
- mailbox / watcher / manager 这种结构比纯文档更能跑
- team config + watcher + task state 是恢复闭环关键

### 从实战博客学到的
- 先测通信再开工
- session 隔离能减少上下文污染
- 模型 / label / 路由 / deliverables 都是常见坑

## 七、故障恢复逻辑（中文）

### 1. specialist 挂掉怎么办
- 检查最近 session
- 看历史是否长时间没推进
- 先催办
- 再返工
- 最后重建新 specialist

### 2. Lead 挂掉怎么办
- 主Agent 接管编排
- 把未完成子任务重新挂回队列
- 必要时重建 lead

### 3. Review 中断怎么办
- 检查是否已有部分评分卡
- 有则续跑，没有则重开 reviewer session

### 4. Group 整体失败怎么办
- 废弃低分组
- 按能力缺口重新招聘
- 保留高通过率经验到能力模板

### 5. Inspect 中断怎么办
- 主Agent 临时执行一次巡检
- 再重启检查Agent

## 九、平台原生层 vs 仓库脚本层

这点必须明确，不然后面会越写越混：

### 平台原生层
- `sessions_spawn`
- `sessions_send`
- `sessions_list`
- `sessions_history`
- `sessions_yield`
- `tools.agentToAgent.enabled`
- `tools.agentToAgent.allow`
- 显式技能入口（如 `/mac` 命令桥）

### 仓库脚本层
- 安装脚本
- 自检脚本
- smoke test
- runtime demo
- 研究资料抓取与整理

结论：
- skill 负责规则、流程、边界、中文伪代码、纪律
- OpenClaw 平台负责真正的 session 与 tool 运行
- 仓库脚本只做安装、自检、演示、落盘与回归，不替代平台能力本身
- 恢复烟雾测试：`tests/test_recovery_pipeline_smoke.py`

## 九、结论

这套系统的关键不是“agent 数量多”，而是：

1. **主Agent唯一出口**
2. **已有会话优先复用**
3. **缺口角色才动态创建**
4. **审核、巡检、恢复闭环真实存在**
5. **状态、日志、队列、评分卡都能留痕**
6. **最终结果只有一个、且去重过**
