## 二、这些优秀作品里最值得学的，不是“角色多”，而是“闭环完整”

观察下来，共同点非常明显：

1. **先定义角色边界**，再让角色工作
2. **先定义任务状态机**，再做并行
3. **先定义 handoff 协议**，再谈 agent 通信
4. **先把失败当正常状态**，再补恢复动作
5. **主控层只做调度、审核、收口**，不下场和 worker 抢活

所以真正值得学的，是这套推导逻辑：

```text
复杂任务会分阶段
=> 分阶段就需要状态机
=> 有状态机就需要 handoff 协议
=> 有 handoff 协议就能让多个 agent 并行
=> 多个 agent 并行后一定会分叉、卡住、重复
=> 所以必须补 reviewer / inspect / recovery / dedupe
=> 最后必须让一个主Agent收口，避免多出口污染用户体验
```

这条链，比“先堆很多 Agent 名字”扎实得多。

## 3.1 OpenClaw 官方文档（Pi 集成架构）

### 最重要的启发

OpenClaw 平台本身已经有：

- session 生命周期
- tool 注入
- system prompt 组合
- skills 触发
- event subscribe
- message / cron / browser / gateway / sessions 等工具
- TUI / Gateway / CLI 多入口

### 对我们 skill 的直接启发

**不要在 skill 层重复发明平台。**

正确分层应该是：

#### 平台层做什么
- 创建 session
- 注入工具
- 保存 session
- 提供消息与执行通道
- 提供 CLI / TUI / Gateway

#### skill 层做什么
- 决定什么时候需要多会话
- 决定创建哪些角色
- 决定消息治理规则
- 决定审核、恢复、去重策略
- 决定何时扩编、何时降级为最小团队

### 可借鉴的项目骨架

```text
platform/
  session-manager
  tool-adapter
  model-resolution
  event-subscribe
  prompt-builder

skill/
  role-policy
  task-packet
  routing-policy
  review-policy
  recovery-policy
  message-governance
```

### 可借鉴的伪代码

```text
用户输入 -> 平台创建/复用 session -> skill 判断是否多会话
-> 如果需要多会话：spawn/send/history/list/yield 串起来
-> 各 worker 独立跑 -> reviewer 检查 -> inspect 兜底
-> 主Agent 合并去重 -> 用户只看到最终结论
```

## 3.2 ClawHub: Agent Team Orchestration

### 它最值得抄的地方

它不是一上来设计大团队，而是先给出 **最小 2-Agent Team**：

- Orchestrator
- Builder
- Reviewer（按需加）

这非常对。

### 它的骨架推导方式

```text
先有任务
=> 任务需要状态
=> 状态需要状态机
=> 状态转移必须由 orchestrator 负责
=> handoff 必须说明：做了什么 / 产物在哪 / 怎么验证 / 有什么风险 / 下一步是什么
=> reviewer 负责阻止质量漂移
```

### 可直接吸收的要点

#### 1. Handoff 五件套
任意 agent 完成交接时都必须说明：

- 做了什么
- 产物在哪
- 怎么验证
- 已知问题
- 下一步是谁来接

#### 2. Orchestrator 不下场干活
这是大多数多 agent 系统最容易崩的点。

#### 3. Failed 是合法终态
不是所有任务都一定要“成功完美结束”。

### 推荐吸收到我们 skill 的伪代码

```text
如果任务简单:
  主Agent 自己完成
否则:
  主Agent 只负责任务拆解与调度
  worker 负责产出
  reviewer 负责否决和回退
  inspect 负责发现卡住并触发恢复
```

## 3.3 zelikk 两篇 TUI 实战

### 关键价值

这两篇文章价值很高，因为它们不是纯概念，而是暴露了 **真实使用 OpenClaw 多 Agent 时的坑**。

### 提炼出的真实经验

#### 1. Agent 与 session 一定要分清
- 同一个 agent 可以有不同 session
- 多个 SSH/TUI 可以同时观察不同 agent / session
- `/agent` 在 TUI 里很关键

#### 2. 多 agent 通信不能想当然
文章明确提到：
- 要强调使用 `sessions_send`
- 尽量不要让模型乱用 label
- 最好用 `sessionKey`
- 发出方不要傻等返回，可用 `timeoutSeconds=0`

#### 3. 先测通信，再做复杂任务
这点特别值得写进安装验收里。

#### 4. 不要用 `/new` 搞乱 session
对于协作系统，这种“无意中新建 session”很容易让 agent-to-agent 路由混乱。

### 这些经验可转成我们的流程纪律

```text
安装后验收顺序：
1. 先看 agent 数和 session 数
2. 逐一测试 agent -> agent 互发消息
3. 再让 leader -> worker 发任务
4. 没有通过通信测试前，不进入复杂任务
```

## 3.4 OpenMOSS

### 它真正强的地方

OpenMOSS 强在：

- 任务 / 子任务状态机完整
- review / score / log / patrol 分层清楚
- 有明确的数据模型
- planner / executor / reviewer / patrol 的职责是分开的

### 它对我们 skill 的启发

我们不一定要把 OpenMOSS 整套搬过来，但它提醒我们：

#### 应该分开的几类状态
- task state
- subtask state
- review state
- score state
- patrol / inspection state
- activity log

#### 应该持久化的几类对象
- agent profile
- task packet
- queue
- log
- review record
- patrol record

### 可借鉴项目骨架

```text
runtime/
  task_store
  queue_store
  review_store
  patrol_store
  score_store

agents/
  main-ceo
  pool-hr
  review-judge
  inspect-patrol
  specialists/

docs/
  role rules
  state machine
  recovery plan
```

### 可借鉴伪代码

```text
任务创建 -> planning
拆解完成 -> active
worker 开始 -> in_progress
提交审核 -> review
审核通过 -> done
审核拒绝 -> rework
异常 -> blocked
blocked 后由 inspect/pool 触发恢复或重派
```

## 3.5 OpenCrew

### 值得学的点

OpenCrew 比较像一套“共享协议 + 流程模板 + 运营规则”。

它的亮点在于：
- A2A 协议清晰
- checkpoint / closeout 模板清晰
- knowledge pipeline 清晰
- 共享规则和模板很多

### 对我们的启发

我们的 skill 也应该继续强化这几件事：

#### 1. 协议先行
不要让 agent 自由发挥消息格式。

#### 2. checkpoint 很重要
多 agent 运行久了，**中间检查点**比最终结果更重要。

#### 3. closeout 不能只是一句话
收尾应该说明：
- 产出物
- 决策依据
- 风险
- 未完成项
- 建议后续动作

### 可借鉴伪代码

```text
每个阶段结束:
  写 checkpoint
  记录 artifacts / decisions / blockers

任务关闭前:
  写 closeout
  更新 memory/log/queue
  生成主Agent最终答复
```

## 3.6 ClawTeam-OpenClaw

### 它的亮点

这个项目更偏“系统化团队框架”，尤其值得学的是：

- mailbox / transport 抽象
- manager / watcher / waiter 分层
- plan / tasks / sessions 分离
- workspace 与 git 留痕
- 对 spawn backend 做抽象

### 对我们的启发

#### 1. transport 要抽象
我们的 skill 虽然主打 OpenClaw 原生 session，但内部仍可以抽象为：

- p2p 通信
- broadcast
- shared context

#### 2. watcher / waiter 不能混在主调度器里
检查、等待、恢复逻辑，最好独立于主 orchestrator。

#### 3. git 留痕是第一等公民
这和你的要求高度一致。

### 可借鉴项目骨架

```text
orchestrator/
  manager
  planner
  reviewer
  deduper

transport/
  p2p
  broadcast
  shared-context

runtime/
  watcher
  waiter
  recovery

workspace/
  artifacts
  logs
  memory
  queue
  git
```

## 4.2 推荐运行逻辑

```text
用户输入
-> 主Agent 判断是否需要多会话
-> 需要则生成 task packet
-> AgentPool 判断复用/招聘与 A/B 编组
-> worker 并行执行
-> reviewer 打分/驳回/择优
-> inspect 观察 stale / retry / redispatch / rebuild
-> 主Agent 去重、合并、去噪、只输出一条用户可见结论
-> git 记录 + memory/log/queue 落盘
```

```text
通信类型：
1. 点对点 p2p
2. 组广播 broadcast
3. 共享上下文 shared context

消息类型：
- task_assign
- task_ack
- task_progress
- task_result
- task_reject
- agent_ping
- recovery_action
- review_scorecard
- closeout
```

## 五、可以直接写进 skill 的中文伪代码

```text
当用户发来任务:
  主Agent先判断:
    是否复杂?
    是否缺信息?
    是否需要多会话?

  如果不复杂:
    主Agent 单会话完成
    输出结果
    结束

  如果复杂或用户输入 /mac:
    主Agent 生成任务包
    AgentPool 判断角色缺口

    如果已有合适 session:
      复用
    否则:
      创建最小够用团队

    如果需要高可靠性:
      建立 A组(稳定) 与 B组(激进)

    向每个 worker 下发 JSON 任务包

    检查Agent 周期性检查:
      最近是否有产出?
      是否卡住?
      是否需要 retry / 重派 / 重建?

    审核Agent 对各组结果评分:
      Reviewer
      Judge
      Metrics

    如果两组都不达标:
      AgentPool 淘汰低质量角色或整组
      重新编组

    如果有通过结果:
      主Agent 做消息治理:
        去重
        合并异步回执
        删除内部噪音
        只保留最新有效结论

      主Agent 向用户输出
      最后写入 memory/log/queue/git
```

## 六、最终结论

这轮学习后，最清楚的结论是：

**多 Agent 协同的核心，不是“创建很多 Agent”，而是“把 session 调度、结构化 handoff、审核、恢复、去重收口，串成一个稳定闭环”。**

这也正是 `Multi-Agent-Collaboration` 应该继续强化的方向：

- 更 OpenClaw 原生
- 更少伪平台层
- 更强 session 闭环
- 更强中文伪代码与流程说明
- 更强安装后可验收性
- 更强 research -> review -> absorb 的自进化机制
