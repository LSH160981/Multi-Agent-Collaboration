# 多agent协同研究总纲（2026-03-27）

> 本文是 `Multi-Agent-Collaboration` 当前保留的**长期研究结论总纲**。目标不是堆链接，而是收口：
> - 平台与 skill 的边界
> - 多 agent 协同的项目骨架
> - 中文伪代码/逻辑流程应覆盖哪些点
> - 多 agent 通信与协调的关键规律
> - 从优秀作品中真正值得吸收的部分

---

## 一、总原则

### 1. Agent = OpenClaw session
不是概念标签，不是文档职位，而是能被 `sessions_spawn / sessions_send / sessions_list / sessions_history / sessions_yield` 真实调度的会话。

### 2. 主Agent是唯一用户出口
这是最高纪律。

- 其他 agent 禁止直接联系用户
- 用户可见消息必须先去重、去噪、合并异步回执、删除内部中间态
- 最终只保留主Agent收口后的一个最新有效结论

### 3. 多 agent 不等于预建一大堆角色
更稳的路线是：

- 先理解任务
- 再决定是否需要多会话
- 优先最小团队
- 缺角色再招聘/复用
- 必要时再 A/B 双组竞争

### 4. 先 research，再审核，再吸收
外部资料不能直接污染主 skill。

正确顺序：
1. 抓取或收集资料
2. 落 `research/`
3. 提炼结论到 `docs/research/`
4. 审核哪些该吸收
5. 主Agent 决定改 `skills/` / `docs/` / `scripts/`
6. git 留痕

---

## 二、平台层 vs skill 层

## 1. 平台层负责什么
OpenClaw 平台原生已经提供：

- session 生命周期
- skills 触发
- tool 调用
- gateway / tui / cli
- browser / message / cron / memory / sessions 等能力

所以本项目**不应该重新发明平台**。

## 2. skill 层负责什么
本 skill 应负责：

- 什么时候切入多会话
- 角色边界与公司化纪律
- 任务包 / handoff / JSON 通信契约
- review / inspect / patrol / recovery / dedupe
- 默认接管、`/mac` 强触发、安装、自检、验收

一句话：

> 平台负责“能跑”，skill 负责“怎么协作、怎么收口、怎么恢复”。

---

## 三、优秀作品共同的推导链

真正值得学的不是“角色多”，而是这条推导链：

```text
复杂任务不适合一个上下文硬扛
-> 需要拆任务
-> 拆任务后需要角色边界
-> 多角色协同需要 handoff 协议
-> handoff 之后需要状态机
-> 状态机运行后一定会出现卡住/返工/重复/冲突
-> 所以必须加入 reviewer / patrol / dedupe / recovery
-> 最后必须由主Agent统一收口，避免用户看到多出口噪音
```

这条链是我们 skill 的主线。

## 四、优秀作品里最值得吸收的部分

## 1. OpenClaw 官方能力

关键启发：
- skill 不应再造平台
- 真正的原生协作应逐步落到 `sessions_*` 工具

可吸收：
- 继续把 runtime 编排往原生 session tools 收
- 文档里持续强调平台层与 skill 层边界

## 2. ClawHub Agent Team Orchestration

关键启发：
- 最小有用团队是 orchestrator + builder + reviewer
- handoff 五件套非常重要：
  - 做了什么
  - 产物在哪
  - 怎么验证
  - 已知问题
  - 下一步是谁接
- orchestrator 不应亲自下场当 worker

可吸收：
- 最小团队优先
- Reviewer 保持硬否决权
- Handoff 契约继续加强

## 3. opencrew

关键启发：
- A2A 协议与任务包要足够自包含
- `sessions_send` 才是真正触发协作
- memory / review / ops 分层清晰

可吸收：
- 任务包自包含
- 不假设子会话天然继承主会话背景
- review / ops / execution 分层

## 4. OpenMOSS

关键启发：
- planner / executor / reviewer / patrol 四角闭环合理
- task / subtask / review / score / log 拆分清楚
- patrol 是一级角色，不是散补丁

可吸收：
- 审核Agent / 检查Agent 的定位要继续强化
- 状态机与日志留痕要继续收紧

## 5. ClawTeam-OpenClaw

关键启发：
- 邮箱、生命周期、事件日志、广播/点对点消息分类清晰
- lead / idle / shutdown / approval 都是合法状态

可吸收：
- 恢复测试不只测 happy path
- 点对点 / 广播 / 生命周期消息需要类型化理解

## 6. zelikk 两篇 TUI 实战

关键启发：
- 先测试 agent 通信，再做复杂任务
- `sessionKey` 比 `label` 更稳
- `/new` 容易把 session 协作链搞乱
- TUI 多窗口观察很适合验收与排障

可吸收：
- 安装验收顺序应固定为：
  - 自检
  - 握手
  - 静默任务
  - runtime / stage3 smoke
  - 恢复测试

## 五、对本仓库的长期结论

## 1. 结构结论
仓库应长期维持这种边界：

```text
skills/   -> 给 OpenClaw 读的 skill 骨架
scripts/  -> 正式入口与可复用实现
tests/    -> smoke / regression / acceptance
research/ -> 原始资料、抓取、过程产物
docs/     -> 长期结论与工程说明
```

## 2. 运行结论
真正稳的运行顺序是：

```text
用户任务
-> 主Agent判断是否启用多会话
-> AgentPool 复用/招聘角色
-> sessions_send / sessions_spawn 派单
-> worker 执行
-> reviewer 审核
-> inspect 巡检与恢复
-> 主Agent 去重收口
-> 用户只收到一个最终答案
```

## 3. 恢复结论
恢复不能只修 `pipeline-state.json`，还要覆盖：

- unknown stage
- stage1 / stage2 / stage3 不完整
- worker session stale
- reviewer 缺席
- lead 缺席
- inspect 缺席
- 全组失败后的 rebuild / 降级

当前仓库已开始把恢复逻辑做成场景矩阵，这条线是对的。

## 4. 自学习结论
自学习要分层：

- `research/auto/`：自动抓取与学习中间产物
- `docs/research/`：提炼后的长期结论
- 主 skill / docs / scripts：审核后再吸收

绝不能直接让自动化脚本野蛮改主规则。

---

## 六、中文伪代码/逻辑流程应该长期保留的主题

至少应继续覆盖：

1. 主Agent 任务理解与追问
2. AgentPool 招聘 / 复用 / 边界控制
3. A/B 双组竞争逻辑
4. JSON A2A 通信协议
5. Handoff 五件套
6. 审核评分与驳回逻辑
7. 巡检与恢复逻辑
8. 用户可见消息去重治理逻辑
9. 自学习 -> 审核 -> 吸收闭环

---

## 七、一句话总结

优秀作品真正共同强的地方不是“agent 多”，而是：

> **平台边界清楚、角色边界清楚、任务包自包含、handoff 严格、状态机明确、恢复可回归、主出口唯一。**

这也是 `Multi-Agent-Collaboration` 应继续坚持的长期路线。
