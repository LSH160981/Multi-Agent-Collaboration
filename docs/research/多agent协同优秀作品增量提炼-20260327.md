## 二、网页资料最值得吸收的点

## 1. OpenClaw Pi 集成架构

关键启发：
- OpenClaw 已经把 session、tool、system prompt、event subscribe、channel delivery 全接好了
- skill 不应再造平台，只应造“协作规则层”

可吸收：
- 把“平台层 vs skill 层”写得更明确
- 明确我们最终目标是 `sessions_spawn/sessions_send/...` 原生编排，而不是长期依赖 shell 包装

## 2. ClawHub Agent Team Orchestration

关键启发：
- 最小有用团队是 orchestrator + builder + reviewer
- handoff 要写清：做了什么 / 产物在哪 / 怎么验 / 已知问题 / 下一步
- orchestrator 不应该自己下场当 worker

可吸收：
- 我们的协议文档要更强调 handoff 五件套
- 我们的 reviewer 应继续保持硬否决权

## 3. Agent Directory

关键启发：
- 可以把外部 skill/service 目录当作持续学习源
- 但不能直接把外部 skill 原样并入主规则

可吸收：
- 自动学习流程必须是：发现 -> research -> 审核 -> 吸收

## 4. zelikk 的 TUI 多 Agent 两篇

关键启发：
- TUI 中 `/agent` 对切换 agent/session 很关键
- 复杂任务前先做 agent 间通信测试
- 用 `sessions_send` 时尽量明确 sessionKey，不要让模型乱猜 label
- 少乱用 `/new`，避免 session 污染

可吸收：
- 安装验收顺序：先自检 -> 再握手 -> 再静默任务 -> 再恢复
- 命令文档里单列 TUI 常用命令与易错点

## 三、GitHub 仓库中最值得学的“骨架与推导”

## 1. opencrew

### 值得学的地方
- 有明确的 `TASK_PROTOCOL`
- 有 `SUBAGENT_PACKET_TEMPLATE`
- A2A 协议强调：真正触发协作的是 `sessions_send`
- daily memory / long-term memory / review / ops 分层清楚

### 提炼出来的项目骨架

```text
shared/
  TASK_PROTOCOL
  A2A_PROTOCOL
  SUBAGENT_PACKET_TEMPLATE
  OPS_REVIEW_PROTOCOL

workspaces/
  cos/
  cto/
  builder/
  research/
  ko/
  ops/
```

### 可吸收做法
- 让任务包自包含，不能假设子 agent 继承主会话人格背景
- A2A 要把“真正触发”和“可见锚点”分开理解
- memory 分 daily 与 long-term 两层
- review / ops 不能和执行混在一起

### 可转成我们的中文伪代码

```text
如果要派给内部会话：
  先准备自包含任务包
  明确目标、边界、交付物、DoD
  用 sessions_send 或 sessions_spawn 真正触发
  不把主会话隐性背景当作对方已知事实
```

## 2. OpenMOSS

### 值得学的地方
- planner / executor / reviewer / patrol 四角关系清楚
- task / subtask / review / score / log 结构完整
- patrol 把“巡检”当成一级角色，而不是零散补丁

### 提炼出来的项目骨架

```text
app/
  models/
  routers/
  services/

skills/
  task-planner-skill/
  task-executor-skill/
  task-reviewer-skill/
  task-patrol-skill/
```

### 可吸收做法
- 保持角色边界强约束
- 状态机要写清：pending -> assigned -> in_progress -> review -> done
- 日志与审查记录要独立留痕

### 对我们 skill 的直接价值
- 审核 Agent / 检查 Agent 的定位是对的，应继续强化
- 每个 agent 独立 memory/log/queue 的方向是对的

## 3. ClawTeam-OpenClaw

### 值得学的地方
- 把邮箱、任务、生命周期、session、transport 拆成明确模块
- inbox / mailbox / plan approval / lifecycle 很清楚
- 强调 leader 审批、广播、点对点消息、事件日志

### 提炼出来的项目骨架

```text
team/
  mailbox.py
  lifecycle.py
  manager.py
  tasks.py
  watcher.py
  waiter.py

spawn/
  sessions.py
  registry.py
  subprocess_backend.py
  tmux_backend.py

transport/
  file.py
  p2p.py
```

### 可吸收做法
- agent 间通信要有事件日志
- 点对点消息、广播消息、生命周期消息要区分类型
- lead / shutdown / idle / approval 都是合法状态，不要只设计 happy path

### 对我们 skill 的直接价值
- 我们虽然走 OpenClaw 原生 session，不走文件邮箱，但“消息类型化”和“事件日志化”非常值得借
- 检查 Agent 的 `idle / stale / shutdown / rebuild` 语义可以更明确

## 4. golutra

### 值得学的地方
- 强调长期运行、CEO Agent、分层记忆、长周期自治
- 强调可视化监控、日志查看、手机远程介入

### 可吸收做法
- 我们可以保留“长期自治”的目标，但必须先把审计、恢复、记忆层打扎实
- 不要先吹一个月自治，要先把每次任务的闭环打通

## 四、综合提炼：别人是怎么推导出多 agent 协同系统的

把几个优秀作品合并后，能看出一条比较稳的推导链：

```text
复杂任务不适合一个上下文硬扛
-> 需要拆任务
-> 拆任务后需要角色边界
-> 有多个角色后需要 handoff 协议
-> 有 handoff 后需要状态机
-> 有状态机后会遇到卡住/返工/重复/冲突
-> 所以必须加入 reviewer / patrol / dedupe / recovery
-> 最后必须有一个主Agent收口，避免用户看到多出口噪音
```

这条推导链，正是我们 skill 应该继续强化的主线。

## 五、对我们仓库的直接改进建议

### 1. 保留最小常驻团队
安装后只常驻：
- `main-ceo`
- `pool-hr`
- `review-judge`
- `inspect-patrol`

specialist 一律按需创建/复用。

### 2. 文档里更明确写出 OpenClaw 真实配置字段
- `tools.agentToAgent.enabled = true`
- `tools.agentToAgent.allow = [...]`
- 建议 `tools.sessions.visibility = all`
- 建议 `commands.nativeSkills = auto`

### 3. 自学习继续放 research，不直接自动改主 skill
正确顺序：
- 搜集资料
- 提炼
- 审核
- 决策吸收
- git 留痕

### 4. 继续强化中文伪代码与中文逻辑流程
这是本仓库的优势，也是你明确要求的交付物。

### 5. 继续把 runtime demo 往原生 session tools 推
- dispatch -> `sessions_spawn` / `sessions_send`
- inspect -> `sessions_list` / `sessions_history`
- 收口等待 -> `sessions_yield`

## 六、一句话总结

优秀作品真正共同强的不是“agent 多”，而是：

> **角色边界清楚、任务包自包含、handoff 严格、状态机明确、审查恢复成体系、主出口唯一。**

这也是 `Multi-Agent-Collaboration` 下一步最该继续加固的主线。
